# 카메라를 켜면 대시보드 애니메이션이 끊김

## 환경

- macOS 26.6.1, Apple Silicon arm64, 120Hz 화면, Electron 44.11.1, `@mediapipe/tasks-vision` 0.10.21
- 빌드된 앱(`out/`)을 임시 기록 폴더와 Chromium 가짜 카메라(`--use-fake-device-for-media-stream`)로 실행. 실제 기록·카메라는 쓰지 않음.

## 재현과 증상

- 사용자 보고(2026-11-17): DMG로 설치한 앱에서 대시보드 애니메이션이 뚝뚝 끊기고 정원도 조금 끊김.
- 측정: `npm run build && npm run perf:animations`. 목표 8회·텀블러 500ml로 첫 설정 후 오늘 화면과 정원을 15초씩 동시에 측정(카메라 끔 → 켬).
- 지표: 화면 갱신(requestAnimationFrame) 간격으로 구한 빠진 화면 비율, 50ms 넘는 긴 작업(Long Task) 수·평균, 프로세스 CPU.

## 원인 (측정으로 확인)

카메라 분석(물체·확대 물체·얼굴·자세 모델, CPU 실행)이 대시보드 화면과 같은 메인 스레드에서 0.25초마다 돌았다. 한 번에 약 90ms 동안 화면을 그리지 못해 초당 4번 끊겼다. 카메라를 끄면 긴 작업이 0회였다. 정원은 별도 창이라 영향이 거의 없었다.

## 해결

- 분석 코드를 `cameraAnalyzer.ts`로 분리하고 배포 앱에서는 Worker(`cameraWorker.ts`)에서 돌린다. 화면 쪽은 0.25초마다 `createImageBitmap`으로 영상 한 장을 넘기고 결과(미리보기 표시·판정 상태·감지 여부)만 받는다. 이전 분석이 끝나기 전에는 새 장을 보내지 않는다.
- MediaPipe는 실행 파일을 `importScripts`로 불러오므로 일반(classic) Worker가 필요하다. Vite `?worker&inline`(빌드 시 IIFE, blob URL)로 만들고 CSP에 `worker-src blob:`를 추가했다.
- 개발 모드(`npm run dev`)는 Vite 개발 서버 Worker가 모듈 방식이라 MediaPipe를 불러올 수 없어 기존처럼 화면 쪽에서 분석한다. 개발 모드에서는 끊김이 남는다.
- 판정 규칙·기준값은 바꾸지 않았다.

## 재검증 (수정 전 1회, 수정 후 3회, 각 15초)

| 항목                    | 수정 전 (카메라 켬)        | 수정 후 (카메라 켬, 3회) |
| ----------------------- | -------------------------- | ------------------------ |
| 대시보드 긴 작업        | 60회, 평균 91ms·최대 103ms | 0회 / 0회 / 0회          |
| 대시보드 빠진 화면      | 31.2%                      | 0.3% / 0.4% / 0.3%       |
| 대시보드 50ms 넘는 멈춤 | 60회                       | 0회 / 0회 / 0회          |
| 대시보드 FPS            | 82.6                       | 119.5 / 119.8 / 119.6    |
| 정원 빠진 화면          | 0%                         | 3.3% / 1.2% / 0.6%       |
| 앱 전체 CPU             | 46%                        | 44% / 38% / 51%          |

- 카메라를 끈 상태는 수정 후 대시보드·정원 모두 긴 작업 0회, 빠진 화면 0%.
- 수정 전 카메라 끔 대시보드 측정은 창이 약 12초 가려져 빠진 화면 비율을 쓸 수 없었다(긴 작업 0회는 유효).
- 수정 후 분석 중에도 카메라 상태가 '사용 중'으로 유지되고 오류 표시가 없었다. 화면 처리 CPU가 카메라 끔 11%에서 켬 31~42%로 늘어 분석이 계속 돈 것을 확인했다.

## 추가 개선: 쉬는 동안 분석 간격 늘리기

- Worker로 옮겨도 분석량은 같아 화면 처리 CPU가 카메라를 켜면 코어 1개 기준 31~42% 들었다.
- 쉬는 동안은 1초에 한 번만 분석하고, 손이 가슴 위로 오르거나(확대 영역 생성)·용기를 잡거나·손이 입 근처거나·마시는 단계가 시작되면 그 뒤 4초 동안 0.25초마다 분석한다(`analysisDue`, 테스트 추가).
- 측정: 같은 빌드에서 간격만 바꿔 20초씩 2회. CPU는 측정 구간 동안 쓴 CPU 시간으로 계산(코어 1개 = 100%). 가짜 카메라 영상에는 사람이 없어 '쉬는 동안' 상태다.

| 카메라 켬 (2회)                               | 항상 0.25초       | 쉬는 동안 1초   |
| --------------------------------------------- | ----------------- | --------------- |
| 화면 처리 CPU                                 | 37.6% / 33.6%     | 24.4% / 22.9%   |
| 카메라로 늘어난 화면 처리 CPU(카메라 끔 대비) | +21.7%p / +19.6%p | +9.0%p / +7.5%p |
| 앱 전체 CPU                                   | 54.6% / 48.8%     | 47.2% / 43.6%   |
| 대시보드 빠진 화면                            | 0% / 0.1%         | 0% / 0%         |

- 카메라가 더하는 화면 처리 CPU가 평균 20.7%p에서 8.3%p로 약 60% 줄었다.
- 손을 든 뒤에는 이전과 같은 0.25초 간격이라 그 상태의 CPU는 '항상 0.25초'와 같다. 사람이 있는 영상으로는 측정하지 않았다.
- 위험: 손을 드는 순간은 최대 1초 늦게 알아챌 수 있다. 아주 빠르게 마시는 경우(1초 안팎)를 놓치는지 실제 카메라로 확인이 필요하다.
- 카메라를 꺼도 그래픽 처리 CPU가 17~23% 든다. 계속 도는 CSS 애니메이션 때문으로 추정하며 다음 개선 후보다.

## 남은 문제

- 카메라를 켜면 정원에서 50ms 넘는 멈춤이 15초에 1~3회 생긴다. 정원 창 자체의 긴 작업은 0회라, Worker가 CPU를 쓰는 동안의 시스템 경합으로 추정한다(미확인).
- 측정은 메인 스레드 기준이라 투명 정원 창의 그래픽 합성 끊김은 보이지 않는다. 카메라를 끈 상태의 GPU 사용률 14~17%는 계속 도는 CSS 애니메이션 때문으로 추정하며 별도 확인이 필요하다.
- 가짜 카메라 영상에는 사람이 없어 실제 감지 정확도는 이 측정으로 확인하지 않았다. 실제 카메라로 감지가 이전과 같은지 사용자 확인이 필요하다.
