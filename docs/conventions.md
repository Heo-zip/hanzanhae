# 개발 규칙

## 구조와 책임

| 위치                         | 역할                                                 |
| ---------------------------- | ---------------------------------------------------- |
| `src/main/`                  | Electron 창·메뉴, IPC 처리, 제품 규칙과 로컬 저장    |
| `src/preload/`               | 화면에 필요한 기능만 공개하는 연결 통로              |
| `src/renderer/src/app/`      | React 앱 진입과 전체 구성                            |
| `src/renderer/src/features/` | `water`, `garden`, `settings`처럼 사용자 기능별 코드 |
| `src/renderer/src/shared/`   | 화면 내부에서 여러 기능이 사용하는 코드              |
| `src/shared/`                | 메인과 화면이 함께 사용하는 타입 등                  |

빈 폴더는 Git에 저장되지 않는다. 실제 코드가 생길 때 만들거나 추가하며, 쓰이지 않는 계층을 억지로 유지하지 않는다. 기능 내부에만 필요한 코드는 해당 기능에 두고, 실제로 공유할 때 공통 영역으로 옮긴다.

## UI 구현 기준

**실제 앱의 UI는 `design` 폴더의 HTML 시안을 그대로 반영한다.** UI를 구현하거나 변경하기 전에 해당 파일과 `design/assets/`를 확인한다.

| 화면                    | 기준 파일                                  |
| ----------------------- | ------------------------------------------ |
| 작은 정원과 물뿌리개    | [garden.html](../design/garden.html)       |
| 오늘·기록·설정 대시보드 | [dashboard.html](../design/dashboard.html) |

- 레이아웃, 여백, 크기, 색상, 글꼴, 아이콘, 문구, 상태별 모습과 애니메이션을 시안에 맞춘다. 화면 크기에 따른 배치 변화도 확인한다.
- 시안의 예시 데이터와 브라우저 전용 데모 스크립트를 실제 제품 정책으로 복사하지 않는다. 미리보기용 조작 패널도 실제 앱 UI에서 제외한다.
- 시안과 확정된 기획의 기능·저장·보안 규칙이 다르면 화면의 외형은 유지하고 동작은 확정된 규칙을 따른다. 사용자가 이후 디자인 변경을 요청하면 최신 요청을 우선한다.
- 시안에 없는 최초 설정·오류 등의 화면은 기존 시안의 시각 언어를 이어서 구현하고, 임의로 제품 정책을 확정하지 않는다.
- 구현 후 같은 창 크기와 상태에서 시안과 실제 앱을 비교한다. 외부 글꼴·리소스는 오프라인 사용과 라이선스를 확인한다.

## Git Flow

### 브랜치와 출발점

| 브랜치                             | 역할                         | 출발점    | 병합 대상           |
| ---------------------------------- | ---------------------------- | --------- | ------------------- |
| `main`                             | 배포 가능한 안정 버전        | —         | —                   |
| `develop`                          | 다음 배포를 위한 통합 브랜치 | `main`    | 배포 시 `release/*` |
| `feature/<작업명>`                 | 새 기능                      | `develop` | `develop`           |
| `fix/<작업명>`                     | 일반 오류 수정               | `develop` | `develop`           |
| `docs/<작업명>` / `chore/<작업명>` | 문서 / 설정 등               | `develop` | `develop`           |
| `release/<버전>`                   | 배포 전 점검과 마무리        | `develop` | `main`과 `develop`  |
| `hotfix/<작업명>`                  | 배포된 버전의 긴급 수정      | `main`    | `main`과 `develop`  |

예: `feature/water-record`, `fix/window-position`, `docs/update-api`.

### 작업 순서

1. 현재 브랜치와 작업 중인 변경 사항을 확인한다. 다른 작업의 변경은 보존하고, 전환 시 덮어쓰거나 섞이지 않게 한다.
2. `develop`의 최신 상태에서 목적에 맞는 작업 브랜치를 만든다. 변경 사항이 있어 안전하게 전환할 수 없으면 현재 작업을 임의로 정리하지 않는다.
3. 작업과 검증을 마친 뒤 변경 내용을 확인하고 목적별로 커밋한다. 작업 브랜치는 `develop`으로 병합한다.
4. 배포 시 `develop`에서 `release/<버전>`을 만들어 점검한다. 완료된 결과는 `main`에 병합하고 배포 버전 태그를 남긴 뒤, 배포 중 수정 사항도 포함해 `develop`에 병합한다.
5. 배포 버전 긴급 수정은 `main`에서 `hotfix/<작업명>`을 만든다. 수정 결과를 `main`과 `develop` 양쪽에 반영해 다음 배포에서 빠지지 않게 한다.

GitHub를 통한 병합은 PR로 변경 내용과 검증 결과를 확인하는 방식을 권장한다. 커밋 제목은 영어 타입 접두어와 한국어 내용을 조합한다. `feat: 물 기록 추가`, `fix: 창 위치 복원`, `docs: 기능 명세 정리`, `chore: 개발 환경 구성`처럼 작성한다. 본문이 필요할 때도 한국어로 작성한다. 사용자가 특정 브랜치나 커밋·푸시 방식을 명시하면 해당 요청을 우선한다.

커밋과 푸시 전에는 대상 변경 사항을 사용자에게 보여주고 검증받는다. 이후 변경 범위가 달라지면 다시 확인받는다.

여기서 배포는 macOS용 앱을 `.dmg` 등으로 묶어 사용자에게 전달하는 과정이다. 별도 서버 운영이나 `release/*` 브랜치가 앱 패키징 자체의 필수 조건은 아니다.

브랜치와 원격 추적 상태는 작업 시작 시 `git branch -vv`와 `git status`로 확인한다. 진행 중인 변경은 임의로 이동하거나 폐기하지 않는다.

## 코드 작성

- TypeScript를 사용하고 타입 검사를 통과한다. 화면에서 입력한 값도 메인에서 재검증한다.
- 주석은 한국어로 작성한다. 코드만으로 알기 어려운 이유와 제약에 집중한다.
- 기존 이름과 스타일을 우선 따르고, 함수·변수는 역할이 드러나는 영어 이름을 사용한다. React 컴포넌트는 `PascalCase`를 사용한다.
- 비밀 정보나 실제 사용자 로컬 DB는 저장소에 올리지 않는다. 환경 변수를 도입할 때는 `.gitignore`와 배포 설정을 함께 확인한다.
- 동작을 바꿀 때 관련 제품·API·DB 문서도 함께 확인한다. 미정인 성장 수치를 확정된 규칙처럼 적지 않는다.
- 화면 상태와 사용자 입력은 React에서, 운영체제·저장 기능은 Electron 메인에서 처리하며 Preload는 필요한 함수만 공개한다.
- 화면의 로딩·성공·빈 상태·오류와 키보드·접근 가능한 이름·포커스 표시를 고려한다. 에러 문구에는 사용자가 할 수 있는 조치를 담는다.
- 가능한 값이 정해진 상태는 타입으로 표현한다. 외부 입력은 `unknown` 등으로 받아 확인하며, `any`나 타입 단언으로 오류를 숨기지 않는다.
- 한 기능에서만 쓰는 코드는 해당 기능에 두고, 실제로 여러 기능이 쓰는 코드는 공통 영역으로 옮긴다. `shared`가 기능 구현을 가져오지 않도록 한다.
- 도구를 추가하기 전 현재 의존성으로 해결할 수 있는지와 Electron·macOS 호환성, 라이선스·유지보수·패키징 영향을 확인하고 선택 이유를 PLAN 또는 결정 기록에 남긴다.
- 주석은 코드의 단순 번역보다 이유·제약과 이해하기 어려운 문법에 집중한다. 기능 REPORT에는 배운 개념과 유지보수 메모를 남긴다.

## 개발 명령어

| 명령어              | 용도                                              |
| ------------------- | ------------------------------------------------- |
| `npm install`       | 패키지 설치                                       |
| `npm run dev`       | 개발 모드 실행                                    |
| `npm run lint`      | ESLint 검사                                       |
| `npm run typecheck` | 메인·preload·화면 타입 검사                       |
| `npm run build`     | 타입 검사 후 앱 코드 빌드                         |
| `npm run format`    | Prettier로 프로젝트 파일 서식 정리                |
| `npm run build:mac` | macOS 패키징. 현재 별도 타입 검사는 포함하지 않음 |

ESLint는 코드 규칙·오류 가능성을 확인하고 Prettier는 서식을 정리한다. `npm run format`은 여러 파일을 변경할 수 있으므로 기존 변경 사항을 확인한 뒤 사용한다.

검증 기준은 [테스트 시나리오](testing.md)를 참고한다.
