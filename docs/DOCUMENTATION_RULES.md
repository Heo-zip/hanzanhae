# 문서 작성 및 관리 규칙

## 역할

- `product.md`·`features.md`·`architecture.md`·`database.md`·`ipc-api.md`: 제품과 기술 기준. 설계안과 확정 사항을 구분한다.
- `CONTEXT.md`: 현재 구현, 미구현 및 확인 범위. 과거 이력 전체를 복제하지 않는다.
- `NEXT_TASK.md`: 현재와 다음 작업, 선행 조건과 완료 조건. 장기 전체 계획은 `roadmap.md`에 둔다.
- `DECISION_RECORD.md`: 중요한 결정·이유·대안·영향과 상태. 바뀐 결정은 이전 항목을 남기고 새 항목으로 연결한다.
- `features/`: 기능별 계획과 실제 개발 기록. 문서의 관계와 템플릿은 [기능 문서 안내](features/README.md)를 따른다.

## 생성 시점과 파일 이름

- 새 기능 전: `기능명-PLAN.md`. 오류·결과 문서는 미리 만들지 않는다.
- 실제 오류 발생: 오류마다 `기능명-오류명-ERROR.md`. 추정과 확인한 원인을 구분하며 오류가 없으면 생성하지 않는다.
- 새 기능 구현·검증 완료: `기능명-REPORT.md` 한 개. 단순 버그 수정에는 별도 REPORT를 필수로 만들지 않는다.
- 기능명과 오류명은 소문자 kebab-case를 사용한다. 예: `initial-setup-db-open-ERROR.md`.
- 문서·스타일·환경 설정 작업에는 PLAN·REPORT를 강제하지 않는다. 작업 범위가 크면 필요에 따라 작성한다.

## 기록 품질

- 확정된 정책, 제안·실험, 실제 구현, 실제 검증 결과를 명확히 구분한다. 실행하지 않은 테스트는 통과로 표시하지 않는다.
- 테스트는 명령·환경·결과를 적고, 수동 검증은 대상 환경과 범위를 적는다. 확인하지 않았거나 해당하지 않는 항목도 구분한다.
- 오류 문서는 환경, 재현 방법, 기대·실제 결과, 추정·확인 원인, 해결 방법, 재검증과 남은 문제를 적는다. 민감 정보는 제외한다.
- 기능 REPORT에는 기획 대비 결과, 바뀐 파일, 검증과 제한사항, 다음 작업, 배운 개념과 유지보수 메모를 남긴다.
- 기술 용어는 필요한 곳에서 풀어 쓰고, 판단 근거와 수치·단위·조건을 구체적으로 적는다. 오류 로그는 민감 정보를 제거한다.

## 갱신 시점

- 작업 중 결정·제품 동작·데이터·IPC가 바뀌면 관련 정본과 결정 기록을 갱신한다.
- 작업 후 CONTEXT와 NEXT_TASK를 현재 상태로 갱신하고 기능 REPORT에 관련 문서를 연결한다.
- 오래된 진행 상황을 여러 파일에 중복하지 않는다. 링크와 마지막 확인 범위를 남기고 코드·Notion·시안과 차이가 나면 근거를 확인한다.
- 기존 작업을 소급해서 완료했다고 꾸미거나 실제 발생하지 않은 오류·테스트 결과를 만들지 않는다.
