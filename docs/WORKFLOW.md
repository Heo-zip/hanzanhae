# 개발 작업 흐름

## 시작

1. 현재 브랜치와 미커밋 변경을 확인하고 기존 작업을 보존한다.
2. [현재 상태](CONTEXT.md), [다음 작업](NEXT_TASK.md), [결정 기록](DECISION_RECORD.md)과 해당 기능의 제품·기술 문서를 읽는다.
3. UI 작업은 `design/`의 관련 HTML과 에셋을 확인한다. 시안이 없는 화면은 기존 시각 언어를 따르며 미제공 상태를 기록한다.
4. 새 기능이면 [PLAN 템플릿](templates/FEATURE_PLAN_TEMPLATE.md)으로 목적·범위·데이터·예외·완료 조건을 먼저 작성한다. 사용자가 이미 승인한 범위와 요청을 따르며, 단순 수정에 빈 기획서를 강제하지 않는다.
5. [Git Flow](conventions.md#git-flow)에 맞는 작업 브랜치를 확인한다. 기존 변경을 안전하게 보존할 수 없는 전환은 하지 않는다.

## 개발 중

- PLAN에 정한 범위를 지키고, 변경된 제품·IPC·DB 규칙은 관련 정본과 결정 기록을 갱신한다.
- 실제 오류가 발생하면 [오류 템플릿](templates/DEVELOPMENT_ERROR_TEMPLATE.md)을 사용해 오류별 재현·원인·해결·확인 결과를 남긴다. 오류가 없으면 ERROR를 만들지 않는다.
- 개인정보·로컬 DB 원본·토큰 등 민감 정보는 문서나 로그에 기록하지 않는다.
- 화면은 실제 데이터와 예시를 구분하고, 저장 실패를 성공으로 보이지 않는다.

## 완료 전

1. 변경 범위에 맞는 타입 검사·린트·빌드와 정상·실패 시나리오를 확인한다. 실제 Mac 확인 여부를 분리해 적는다.
2. 새 기능의 구현과 검증이 끝나면 [REPORT 템플릿](templates/RESULT_REPORT_TEMPLATE.md)으로 실제 결과와 미확인 항목을 기록한다. 단순 버그 수정에는 기능 REPORT를 필수로 만들지 않는다.
3. CONTEXT·NEXT_TASK를 갱신하고, 결정 변경이 있다면 DECISION_RECORD와 관련 명세도 갱신한다.
4. 커밋과 푸시 전에 대상 변경을 보여주고 사용자 검증을 받는다. 커밋 제목은 `feat: 물 기록 추가`처럼 영어 타입과 한국어 내용을 쓴다.

이슈와 PR은 필요하거나 요청된 경우에 연결한다. 계획·오류·결과 문서 작성과 별도로 언제나 이슈를 만들어야 하는 것은 아니다.
